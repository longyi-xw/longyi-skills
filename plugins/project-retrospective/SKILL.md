# Project Retrospective（项目复盘 · 知识与经验沉淀）

把一个**已完成**的项目，反向蒸馏成两样东西：

1. **个人知识** —— 架构方式、技术原理、可迁移的解题模式，是给未来的自己看的；
2. **经历证据** —— 带证据链的技能与成果，是给 agent 和面试官看的。

产出的档案有两个消费者：**人**（读 `INSIGHTS.md` 复习思路）和 **agent**（读 `experience.yml` 直接生成简历）。所以档案必须同时是可读的和可解析的。

> 与 `project-onboarding` 的分工：那个建立「往哪加代码」的心智地图；本技能回答「我从中带走了什么可复用的认知，以及怎么证明我做过」。若项目里已有 `PROJECT_OVERVIEW.md`，**先读它**，跳过重复的结构扫描，直接进入难点挖掘。

---

## 两种模式

| 模式 | 触发表述 | 做什么 |
|------|----------|--------|
| **单项目提炼**（默认） | 「复盘这个项目」「总结一下这个项目」「提炼经验」 | 分析一个项目 → 产出四件套档案 |
| **跨项目汇总** | 「汇总我的项目经验」「生成个人技术画像」「帮我写简历」「我要投 X 岗」 | 扫描知识库里已有档案 → 产出 `PROFILE.md` + 简历初稿，见 `references/aggregate-mode.md` |

汇总模式**不重新分析代码**，只消费已生成的 `experience.yml`。若知识库为空，先提示用户至少复盘一个项目。

---

## 阶段 0：确定知识库位置（首次必做，之后不再问）

档案默认**集中存放**在一个个人知识库目录里，跨项目累积，方便以后一次性喂给 agent 生成简历；公司项目的个人复盘也不会污染公司仓库。

**路径解析顺序**（逐级回退，命中即停，不要跳过）：

1. 用户本次明确指定的路径
2. 配置文件 `~/.project-retrospective.json` 里的 `knowledgeBase`
3. 环境变量 `KNOWLEDGE_HOME`
4. **都没有 → 询问用户**，把探测到的建议值作为默认项，写入配置文件后继续

```bash
cat ~/.project-retrospective.json 2>/dev/null   # 有 knowledgeBase 就直接用，别再问
```

**绝不硬编码任何绝对路径**（不要假设 `D:\`、`~/Documents` 之类）。换机器、换系统时配置文件不存在，自然会重新询问一次。首次询问的话术、建议值探测命令、配置文件字段，见 `references/config-and-paths.md`。

首次配置时**顺带确认作者身份**（`git config user.email`，可多个邮箱/GitHub 用户名），用于阶段 1 识别「哪些代码是你写的」。

单项目档案落点：`<知识库>/projects/<项目名>/`。用户明确说「写到项目里」时才写项目根目录。

## 阶段 1：定性与贡献边界

**先划清「这个项目做了什么」和「我做了什么」—— 后者才是简历的主语。**

```bash
git log --format='%ad' --date=short | tail -1                      # 起始时间
git log --format='%ad' --date=short | head -1                      # 最后一次提交
git shortlog -sne --all | head -20                                 # 贡献者与提交占比
git log --author="<你的邮箱>" --oneline | wc -l                     # 你的提交数
git log --author="<你的邮箱>" --name-only --format='' | sort -u     # 你碰过的文件
```

据此确定：项目周期、规模（提交数 / 文件数 / 代码量）、协作人数、**你的贡献占比与负责模块**。

三种情况分别处理：
- **非 git 仓库 / 单人项目**：直接问用户角色与职责范围
- **多人协作**：用上面的文件清单圈出你的主战场，只对这些模块做深度挖掘
- **代码不是你写的（如接手维护）**：如实标注为「维护与重构」，不要把原作者的架构算成自己的设计

> 明确排除：脚手架生成的代码、`node_modules`、构建产物、复制粘贴的模板。这些出现在档案里就是注水。

---

## 阶段 2：难点雷达（本技能的差异化）

**不要问「这个项目有什么难点」然后等用户回答，也不要凭感觉猜。** 难点在代码里留有痕迹，按信号扫描：

| 信号 | 说明什么 |
|------|----------|
| `workaround` `hack` `兼容` `踩坑` `注意` `不能删` 类注释 | 遇到过现成方案解决不了的问题 |
| git log 中改动次数 top 的文件 | 反复调整 = 一次没做对 = 有权衡 |
| 自研而非用库的模块 | 现成轮子不够用，才需要自己造 |
| 重试 / 降级 / 兜底 / 熔断 / 并发控制 | 处理过真实的不确定性 |
| 缓存 / 防抖节流 / 虚拟化 / Worker / 懒加载 | 碰到过真实的性能墙 |
| 数学、几何、编解码、状态机、图算法 | 有算法含量 |
| 长函数 / 深嵌套的核心模块 | 业务复杂度的沉积区 |
| commit message 里的 `fix` `perf` `refactor` | 问题与优化的现场记录 |

扫描命令与逐条判读方法见 `references/mining-playbook.md`。

先扫出**候选清单**，再**读源码验证**每一条：是真难点，还是只是写得乱？留下 3–6 个真正的技术主题进入阶段 3，其余丢弃。宁可少而深，不要多而浅。

---

## 阶段 3：四层抽象阶梯（本技能的灵魂）

对阶段 2 留下的每个技术主题，**逐层往上爬**。只停在 L0/L1 的档案没有价值——那是任何人读一遍 README 都能写的。

| 层 | 问题 | 示例 |
|----|------|------|
| **L0 事实** | 用了什么 | Vue3 + Three.js + Web Worker |
| **L1 机制** | 怎么工作的、原理/算法是什么 | 场景 diff 下沉到 Worker，主线程只收 patch 指令 |
| **L2 决策** | 为什么这么选、放弃了什么、代价是什么 | 放弃虚拟列表方案，因为要支持跨行合并；代价是首帧多一次结构化克隆 |
| **L3 迁移** | 抽象出的通用解法，还能用在哪 | 「重计算下沉 + 结构化增量回传」适用于任何主线程被长任务阻塞的场景 |

**硬性要求：每个主题必须写得出 L2 和 L3。写不出来，说明它不值得进档案，删掉它。**

- L0/L1 是基础分，人人都有；
- **L2 决定你在面试里能不能扛住追问**（面试官只会问「为什么不用 X」）；
- **L3 决定这段经历能不能迁移到下一份工作**，也是「个人知识」区别于「项目说明书」的地方。

正反例对照见 `references/mining-playbook.md`。

---

## 阶段 4：证据链核验（防注水）

**每一条能力主张都必须挂得上证据。** 三种可信度，如实标注，不要模糊：

| 标记 | 含义 |
|------|------|
| `verified` | 有代码位置（`文件:行`）或 commit 哈希支撑 |
| `user_stated` | 用户口述的（团队规模、线上数据、业务背景等代码里没有的事实） |
| `inferred` | 从代码合理推断，但未经确认 |

**明令禁止：**
- 把 `package.json` 里的依赖当成自己的能力（装过 ≠ 懂）
- 把脚手架/模板生成的代码算作个人贡献
- **编造任何量化数字**——没有就是没有，写 `TODO(待补充)`，绝不替用户捏造「性能提升 60%」
- 把「项目有什么功能」写成「我的能力」——复盘的主语始终是你做的事

---

## 阶段 5：追问清单（收集代码里读不到的）

代码能给出技术事实，给不出**背景与成果**——而简历恰恰要这些。分析完主动向用户列出缺口，一次问完：

1. 你在项目里的角色？团队几个人？你独立负责哪些模块？
2. 项目周期多长？是上线了、内部使用、还是练手/未上线？（未上线也不丢人，如实写）
3. 有没有量化数据：用户量、数据规模、QPS、构建时间、包体积、性能优化前后的数字？
4. 最有成就感 / 最难受的一次技术攻坚是什么？（往往是最好的面试故事，代码里看不出来）
5. 有没有需要脱敏的信息：公司名、内部系统名、客户名？
6. 有没有做过但代码里没体现的事：技术选型评审、方案文档、带人、跨团队协作、线上事故处理？

用户可以跳过。跳过的项在档案里标 `TODO(待补充)`，`experience.yml` 里对应字段留空数组而**不是**填一个编的值。

---

## 阶段 6：生成四件套

写到 `<知识库>/projects/<项目名>/`，完整模板见 `references/output-templates.md`：

| 文件 | 给谁看 | 内容 |
|------|--------|------|
| `INSIGHTS.md` | 人 | 架构决策、技术原理、难点攻坚、L3 可迁移经验，含 Mermaid 架构图/流程图 |
| `experience.yml` | **agent** | 结构化的技能标签、证据链、量化成果、角色边界——生成简历时直接消费 |
| `RESUME-SNIPPET.md` | 人（可直接粘） | STAR 格式项目经历条目，附长版（详细）与短版（3 行）两版 |
| `INTERVIEW.md` | 人 | 从项目反推的面试问答：会被问什么、答题要点、追问预案 |

**已存在同名档案时**：先读旧档案，问用户「更新（合并新发现，保留已填的 `user_stated` 内容）还是另存副本」。默认更新——复盘档案本就该随认知迭代。另存时用 `<文件名>_YYYYMMDD_HHMMSS`。**任何情况下不静默覆盖用户已补充的内容。**

生成后在对话里给 3–5 句口头小结：这个项目最值钱的技术资产是哪一两条，以及还缺什么数据。

---

## 关键原则

- **主语是「我」，不是「这个项目」** —— 复盘产出的是个人经历，不是项目说明书。
- **L3 写不出来就别写这个主题** —— 没有可迁移性的技术细节，对未来的你和面试官都没用。
- **证据不足就标注，不要润色** —— 简历里一句站不住的话，会毁掉整场面试。
- **少而深胜过多而全** —— 3 个能扛住追问的主题，好过 10 条技术栈罗列。
- **脱敏是默认动作** —— 公司项目的公司名/内部系统名/客户名，一律替换成描述性称呼（如「某券商资管系统」）。
- **失败与放弃的方案同样值钱** —— 「试过 A 不行，因为 B，最后走了 C」是最有说服力的技术叙事。
