# 跨项目汇总模式

把知识库里已有的项目档案合成两样东西：**个人技术画像**（给自己看清能力版图）和**简历初稿**（可按目标岗位调重点）。

**本模式不重新分析代码**，只消费 `<知识库>/projects/*/experience.yml`。某个项目还没复盘过，先走单项目流程。

## 阶段 A：收集

```bash
ls -d "<知识库>"/projects/*/ 2>/dev/null
cat "<知识库>"/projects/*/experience.yml
```

- 档案少于 2 个 → 提示用户「汇总至少需要 2 个项目，先复盘几个」
- `schema_version` 不是 1 → 按当前 schema 尽力解析，缺字段的标 `TODO`
- 只有 `INSIGHTS.md` 没有 `experience.yml`（手写的旧档案）→ 先读 `INSIGHTS.md` 反向补出 `experience.yml` 再汇总

## 阶段 B：合并与去重

**技能合并**：同名技能跨项目出现时，`level` 取最高，`from` 累积所有来源。

```
Web Worker 并发模型  level: deep     出现 2 次  ← lowcode-3d(h1), qvs(h4)
Three.js 渲染管线    level: applied  出现 1 次  ← lowcode-3d(h1,h2)
```

排序规则：先按 `level`（deep > applied > aware），同级按出现项目数降序。**出现在多个项目里的深度技能，就是你的核心竞争力**——这一点用户自己往往没意识到，要在画像里明确点出来。

近义技能要归并（`Vue3` / `Vue 3` / `Vue Composition API` → `Vue 3`），但**不要把不同层次的东西合并**（`Three.js` 和 `WebGL` 是两回事，后者更底层）。

**Highlight 池**：收集所有 `resume_worthy: true` 的 highlight，按「有量化成果 > 有明确取舍 > 有可迁移抽象」排序备用。

## 阶段 C：归纳技术主线

这一步是汇总模式的价值所在——**不是把项目罗列出来，而是找出它们串起来的那条线**。

看这几个维度：
- **时间线上的能力演进**：早期项目在做什么，最近的项目在做什么，跨过了哪些台阶
- **反复出现的问题类型**：多个项目都碰上性能墙？都涉及跨端通信？都在做工程化？——那就是你的专长领域
- **技术纵深 vs 广度**：是在一个方向越挖越深，还是横向铺开
- **角色演进**：从参与开发到独立负责，团队规模变化

产出一句能概括的定位，例如：

> 前端工程师，主线是**复杂交互场景下的性能与架构治理**——从可视化搭建到量化分析工作台，反复解决「大数据量下主线程被阻塞」这一类问题，手段从分片渲染演进到计算下沉与增量同步。

这句话应该有据可查（点得出是哪几个项目哪几条 highlight 支撑的），不是文学创作。归纳不出主线时**如实说**：能力比较分散，可以考虑往某个方向补齐——这个判断本身对用户有用。

## 阶段 D：产出 `PROFILE.md`

写到 `<知识库>/PROFILE.md`（已存在则更新，保留用户手改的内容）。

```markdown
# 个人技术画像

> 更新于 <日期> ｜ 覆盖 <N> 个项目，时间跨度 <YYYY.MM – YYYY.MM>

## 一句话定位
<阶段 C 的主线，附支撑项目>

## 能力版图

| 技能 | 深度 | 出现项目 | 证据 |
|------|------|----------|------|
| <技能> | deep | <项目1>, <项目2> | <highlight 标题> |

## 技术主线与演进
<时间线叙述：早期 → 现在，跨过了哪些台阶。用 Mermaid timeline 或表格。>

## 最硬的三条经历
<从 highlight 池挑三条最强的，附一句为什么它强（有数据 / 有取舍 / 有迁移性）>

## 项目一览

| 项目 | 周期 | 角色 | 技术栈 | 状态 | 档案 |
|------|------|------|--------|------|------|
| <名> | <期> | <角色> | <栈> | shipped | [INSIGHTS](projects/<名>/INSIGHTS.md) |

## 短板与缺口
<诚实的部分：哪些方向没有项目支撑、哪些技能只到 aware、哪些数据缺失。给出补齐建议。>
```

## 阶段 E：产出简历初稿

写到 `<知识库>/resume/RESUME-<方向>-<YYYYMMDD>.md`。

**先确认目标岗位方向**（用户没说就问，或用配置里的 `defaults.resumeTarget`）。方向决定三件事：

| 决策 | 依据 |
|------|------|
| 项目排序 | 与目标岗位相关度优先，其次时间倒序 |
| Highlight 取舍 | 每个项目挑 2–4 条与岗位最相关的，其余不进简历 |
| 技能栏顺序 | 岗位 JD 关键词优先，其次按 level |

结构：

```markdown
# <姓名> ｜ <目标岗位>

<联系方式：TODO(待补充)>

## 个人概述
<3 行：定位 + 最强的一条能力 + 最有说服力的一个成果。来自 PROFILE.md 的一句话定位，按岗位调整措辞。>

## 专业技能
<按 level 与岗位相关度分组。只写 applied 及以上——aware 的不进简历。>

## 项目经历
<每个项目直接复用 projects/<名>/RESUME-SNIPPET.md 的长版，按方向裁剪 highlight 条数>

## 教育经历 / 其他
TODO(待补充)
```

**生成后必须做的两件事：**

1. **列出所有 `TODO(待补充)`** —— 联系方式、教育经历、缺失的量化数据，让用户一次补齐。
2. **列出脱敏检查项** —— `confidentiality: internal` 的项目里，公司名/系统名/客户名是否都替换了。

## 纪律

- **不跨项目挪移成果**：A 项目的数字不能安到 B 项目上。
- **不合并成一个更大的项目**：两个小项目就是两个，不要为了显得规模大而合写。
- **不升级 level**：汇总时只取已有的最高值，不因为「出现次数多」就从 applied 升成 deep。
- **`inferred` 的内容进不了简历**：只有 `verified` 和 `user_stated` 可以，`inferred` 的先向用户确认。
- **缺口要写出来**：一份诚实标注缺口的画像，比一份看起来完美的有用得多——用户拿它去补，而不是拿它去骗。
